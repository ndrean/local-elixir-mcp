# Local Stdio MCP (`hex_local`) Guidelines

These instructions are a standalone fallback for clients that do not load skills.
For skill-capable clients, install `skills/hex-local/` from this repository instead
of copying this full guide. The skill entrypoint is
[skills/hex-local/SKILL.md](skills/hex-local/SKILL.md); its debugging reference is
loaded only when relevant. The skill does not install or connect the MCP server.
If these tools are unavailable, state that briefly and continue with available
source or official documentation rather than pretending a tool call succeeded.

## MCP Tools Reference

- **`search_docs`**: Search official HexDocs guides, typespecs, and code examples.
  - **`package` is required.** Always extract the target package name from the request (e.g. `boruta`, `anubis_mcp`, `phoenix`, `plug`) and pass it as `package`. The server does not infer package scope from the query text. A missing package produces a notice and no search; a wrong package searches the wrong documentation. Naming an unindexed package is correct — that triggers ingestion after version resolution.
  - **A question spanning several packages is several calls.** Searches are scoped to one package, so decompose and consolidate rather than asking the user to. For "OAuth in anubis_mcp using boruta with Phoenix Plug", issue one `search_docs` per package and merge the results into a single answer. Do NOT send the same sentence to each: write a query per package using the terms *that* package's docs would use — here `"StreamableHTTP Plug router forward authorization"` for anubis_mcp and `"authorize access token bearer Plug"` for boruta.
  - **Keep the package name out of `query`.** It is already scoped by `package`, so repeating it only adds noise: the FTS sanitiser ORs the extra tokens into the search, and they dilute the query embedding.
  - **Grepping vs search_docs**: `grep` on `deps/` reads *source*; `search_docs` reads what the compiler produced, because ExDoc is generated from the `Docs` chunk of the compiled `.beam`. The two disagree wherever a library generates its public API — `Peri.defschema`, `Ecto.Schema`, `use GenServer`, Phoenix routers, Anubis' own component DSL — and there `grep` returns **nothing for a function that exists and is called two lines away**. In `anubis_mcp`, `parse_options!/1` is called at `stdio.ex:48` and generated by `defschema(:parse_options, …)` at line 38; `grep -rn "def parse_options!" deps/anubis_mcp/lib/` matches no line in the package. Use `grep` for implementation detail and call sites in code you can read. Use `search_docs` for a package's public surface, conceptual guides, configuration patterns, examples, or any uninstalled package. `grep` also ranks nothing: forty textual hits arrive in file order, and a question phrased differently from the docs ("how do I avoid re-embedding" against docs that say `chunk_overlap`) has no lexical overlap to match at all. **An empty `grep` for a symbol you know is used is a signal to search the docs, not evidence the symbol is absent.** Check `doc_type`: API documentation includes `module`, `function`, `macro`, `callback`, `type`, `opaque`, and other API row kinds; `extras` identifies hand-written guides. Check important defaults and version-sensitive claims against the matching API or source. A documented generated function can have only a heading, which identifies the API without explaining its behavior.
  - **Version resolution**: an explicit `version` wins, then `$PROJECT_ROOT/mix.lock`, then the server's own BEAM, then Hex latest stable. This resolves the target for ingestion; cached unpinned docs can remain at their indexed version with a drift notice. Read the returned version before claiming to describe the latest release. An unpublished explicit version is refused with the list of real releases.
  - **`app_version` is the *server's* dependency, not yours.** `:application.get_key/2` inspects the running BEAM, which was started from the directory in the MCP config — not the repo you are editing. Packages the server does not itself depend on return `undefined`. Without a matching `PROJECT_ROOT` lock entry, resolution can fall back to Hex latest stable; this tells you nothing about what your project runs.
  - **`PROJECT_ROOT` removes the need to pass `version` at all.** Set it in the server's `env` block to the repo being edited, and the server reads that project's `mix.lock` itself — freshly on every lookup, so `mix deps.get` mid-session is picked up without a restart. Resolution order becomes:

    ```
    explicit version:  ->  $PROJECT_ROOT/mix.lock  ->  the server's own BEAM  ->  Hex latest stable
    ```

    The lockfile is authoritative and may point *backwards*: a project on `boruta 2.3.0` gets 2.3.0 docs even though 3.0.0-beta.4 exists. Refusing to "downgrade" would silently serve documentation for code the project does not run.

    Without `PROJECT_ROOT`, the old rule applies and you must pass `version` yourself: omitting it hands resolution to the server, which sees only its own BEAM and then Hex latest stable, and answers about a different version without saying so.

  - **`PROJECT_ROOT` is per project; the database usually is not.** Sharing one database across projects is the normal setup and needs no configuration — the path is compiled in. Only one version per package is kept, so the cost appears in exactly one situation: two projects pinning *different* versions of the *same* package, which re-ingests on each switch. The search reports it when it happens; the fix is a separate `DATABASE_PATH` for that project, not retries.
  - **When to pass `version` explicitly.** With `PROJECT_ROOT` set, essentially never — pass it only to read a version the project does *not* run (comparing against a newer release, checking what changed). Without it, pass it whenever the answer must match your lockfile.
    - For a package that is **not** a dependency — evaluating a library, reading someone else's docs — omit it initially. Inspect the returned version and notices: cached docs may be retained rather than automatically updated to latest stable.
  - **Elixir's own doc sets work, and are versioned by the server's Elixir.** `elixir`, `eex`, `ex_unit`, `iex`, `logger` and `mix` have no Hex package entry — `hex.pm/api/packages/elixir` 404s — but their docs are published, so they are searchable like any other package. Use them for `Kernel`, `Enum`, `Stream`, `Task`, `GenServer`, `Process`, `String`, ExUnit and Mix. A new ingestion without `version` targets the server's `System.version()`, since `mix.lock` never lists Elixir. Pass the project's Elixir version explicitly when it differs, and inspect the returned version for cached docs. An explicit core-doc version is taken on trust because there is no Hex release list to check.
  - **One version per package.** Ingesting prunes every other version of that package. There is never a mix, and a search never interleaves versions.
  - **`refresh: true`** re-downloads and replaces what is indexed. Use it when docs look stale or the index looks wrong; do NOT pass it routinely, since it costs a full download plus re-embedding of every doc.
    - For a package **in this project's deps**, refresh without an explicit `version` uses the project lock when `PROJECT_ROOT` points at that project. An explicit `version` overrides the lock; without `PROJECT_ROOT`, pass the locked version yourself.
    - For a package **not pinned by the project or loaded in the server**, refresh without `version` resolves to latest stable, which can move you *off* a pinned pre-release. If a notice says the indexed version is "ahead of stable", pass `version: "<stored version>"` alongside `refresh: true` to rebuild in place.
  - **Missing embeddings** are repaired automatically, up to 2 attempts per package/version; after that the payload says so and stops retrying. Rows without an embedding are returned by keyword search but never by vector search, so results are quietly weaker until repaired.
  - Ingestion **aborts rather than saving docs it could not embed**, so a failed ingest leaves the previously indexed rows intact and the payload carries a `notices` entry (e.g. `"Ingestion failed for 'x': {:embedding_failed, ...}"`).
  - **Long ingestions**: a first-time or refreshed package may not finish within the tool call. The payload then carries a notice like `"Docs for 'x' are still being indexed (embedding 7/18, 20s elapsed)"`. The job keeps running — call `search_docs` again to collect its result, but **drop `refresh: true` from the retry**. Retry without `refresh` to collect the existing work instead of requesting another refresh. Never ingest the same package repeatedly in parallel. Make at most two collection retries in the turn; if indexing is still progressing, report that it remains in progress.
  - **Citing Package Versions**: When referencing documentation returned by `search_docs`, **ALWAYS include the package version(s)** returned in the payload (e.g. `anubis_mcp v1.14.0`, `boruta v3.0.0-beta.4`).
  - **No URL Extrapolation / Hallucination**: NEVER construct, guess, or extrapolate HexDocs or GitHub URLs. Only reference exact returned `hexdocs_url` or `source_url` values, or links independently verified. Include the returned package version with the claim; source links may be absent.

- **`list_indexed_packages`**: List what this database actually holds — package, version, doc count, whether embeddings are complete, and `app_version` (the version loaded in the *MCP server's own* BEAM, or `null` when the server does not depend on that package — which says nothing about what your current repo locks).
  - Use it before `refresh: true` on a package you did not index in this session, to see whether refreshing would change the version. `app_version: null` does not establish what the calling project pins; inspect the stored version and project lock before refreshing.
  - Use it when results look wrong or stale, to check `complete?` and the indexed version before assuming the search is at fault.
  - The payload includes `database`, the SQLite file in use. `DATABASE_PATH` is per-server: pointing two projects at one file makes them overwrite each other's rows, since only one version per package is kept.
  - `check_hex: true` adds each package's latest stable release and a `drift` verdict (`current` / `behind` / `ahead of stable`). It costs **one HTTP request per indexed package**, so leave it off unless drift is the question.

- **`recall`**: Search the local knowledge base for past pain points, architectural decisions, and bug fixes. Hybrid retrieval — FTS5 and vector fused by RRF, the same shape as `search_docs` — so a question phrased in different words than the entry still finds it. Falls back to keyword-only when no embedding is available, and works with no API key at all.
  - **Execute BEFORE fixing**:
    1. **On Any Command/Test Failure**: Immediately run `recall(query: "<error message>", kind: "pain_point")`.
    2. **On Second Iteration**: If the first code edit fails to fix an error, run `recall` on the specific function/module before making a second edit.
    3. **Before Modifying Config**: Run `recall` before editing `Caddyfile`, `docker-compose.yml`, `runtime.exs`, or OAuth configs.
  - These rules apply when `recall` is available. An unavailable tool is not a reason to invent results or repeatedly try a missing tool. Recalled lessons are historical evidence: verify that their version and circumstances apply. Legacy or incompatible knowledge vectors are excluded from cosine comparisons; their text remains keyword-searchable.

- **`remember`**: Save technical learnings or pain points to the knowledge base. Takes `texts`, a **list** — pass every lesson from a session in one call. An Anubis session holds one request in flight and queues the rest, so repeated calls buy no parallelism and cost a model turn each; the batch is also curated sequentially, which avoids the rate limiting that concurrent submissions provoke. A single lesson is a one-element list. Returns immediately with a `request_id` per entry — curation runs in the background and may discard, merge or replace what you sent.
  - Acceptance acknowledges queued curation, not a confirmed saved entry. Record the symptom, verified cause, fix, affected version and validation. Exclude secrets and distinguish hypotheses from confirmed findings.
  - **Execute AFTER fixing, when at least one condition applies**:
    1. **The 2+ Attempt Rule**: The fix required 2 or more failed attempts to solve.
    2. **Cross-Boundary Layer Fixes**: Call `remember` if the fix involved interactions between 2+ layers (e.g., Caddy reverse-proxy + Phoenix SSE, Docker networking + Postgres).
    3. **Library Version Quirks**: Call `remember` if the fix involved an undocumented behavior or version constraint in a dependency.
  - Skip routine one-step corrections without a cross-layer cause or dependency quirk.

- **`get_token_usage`**: Query persistent AI token consumption statistics from SQLite.
  - Supports optional `model`, `from` (e.g. `"2026-08-01"`), and `until` date range parameters.

- **`search_hex_packages`**: search Hex.pm names *and descriptions*, ranked by downloads. It answers "which package", not "how does it work" — pair it with `search_docs` once you have the name.
  - **A question that names a technology rather than a package starts here.** "a NATS client", "how do people do HTTP in Elixir", "something for CSV" — `search_docs` cannot answer these, because it needs a package name and will happily ingest whatever you guess. That failure is silent and convincing: you get real documentation for the wrong library.
  - **The name often does not contain the concept.** A search for `nats` can discover **`gnat`**, whose name does not contain the technology. Inspect current results and descriptions instead of guessing a package name or assuming historical download counts still describe the choices.
  - **Downloads separate adoption, not liveness.** They are cumulative, so a once-popular abandoned package still ranks high. When currency matters, confirm with the repository or with `search_github_issues` on its org before trusting the top hit.

- **`search_github_issues`**: live search of GitHub issues **and pull requests**, open and closed. Pass **`package`** (a Hex name) as the normal path — the repository is resolved from Hex metadata, so you never have to know that `anubis_mcp` lives at `zoedsoupe/anubis-mcp`, and the same identifier works across `search_docs` and `list_indexed_packages`. `repo` (`owner/name`) and `org` remain for repositories that are not Hex packages. One of the three is required. `type` (`issue` / `pr`) is optional and omitting it — searching both — is almost always what you want. `limit` defaults to 10 and accepts 1-50; issue bodies come back up to 1500 characters, marked `…[truncated]` when cut.
  - **Execute BEFORE theorising, not after.**
    1. **A dependency behaves unexpectedly**: search its repository before building an explanation. Do not filter to open issues. A *closed* issue plus its merged PR tells you what the maintainer has already accepted as a bug, which is the difference between filing a feature request and pointing at a fix that missed one code path.
    2. **You found a bug in one code path**: search for the same bug in the sibling paths — transports, adapters, backends, storage engines. They are written at different times by different people, so a fix applied to one is routinely absent from the others, and that framing is what makes a patch easy to accept.
    3. **Prefer `gh` when the CLI is available**: Search a verified repository with authenticated `gh` when convenient; leave state unrestricted and search both issues and PRs. This tool exists for when `gh` is absent or unauthenticated — and because a tool in the list gets reached for, while a shell command has to be remembered.

## How `search_docs` retrieves

FTS5/BM25 and exact cosine search each retrieve up to 15 package-scoped rows,
executed sequentially. Reciprocal rank fusion scores their entire union before
selecting up to ten results. For prose queries, heading-only entries, title
restatements, and bare typespecs receive 40% of their RRF score; explanations and
examples keep their full score. Identifier-only queries retain ordinary RRF
ordering. Use a bare exact identifier to look up a generated function whose stub
may rank lower for a prose query. All entries remain indexed. There is no learned
reranker. Read all returned chunks: rank alone does not establish relevance, and
the result set can contain loosely related material.
Historical benchmark scores are regression measurements, not guarantees for new
questions or a different corpus.

Inspect `notices` and, when present, `retrieval_mode`:

- `hybrid`, `keyword`, `vector`, and `none` identify the arms that ran successfully;
  they do not measure relevance or imply that a healthy arm found a match.
- Missing or slow query embedding, model mismatch, and unverified docs provenance
  disable semantic retrieval with a notice. A failed arm leaves the healthy arm
  available. Explain degradation when it limits the answer's confidence.
- Model/configuration problems and exhausted repair budgets need operator action;
  repeating the same query or forcing refresh does not repair them.
- An ingestion-progress or request-deadline notice can arrive before indexing is
  complete. Supervised ingestion continues; retry without refresh as above.
- An empty healthy result is different from failed retrieval or pending ingestion.
  Try a focused reformulation or inspect matching source/upstream issues before
  concluding that the API or feature does not exist.

The foreground tool has a 27-second budget, with up to two seconds for query
embedding. A queued request can still encounter the client's or transport's own
timeout. Issue ingestion-related calls sequentially rather than creating competing
work for the same package. Do not rebuild the whole index or change server settings
as a side effect of a documentation lookup.

## Everything else is in `README.md`

Setup, client configuration, running a release, provider environment variables,
docs and knowledge embedding provenance, ingestion tuning and how to apply code
changes are operator concerns and live there.

They are deliberately not repeated here. This file is loaded into every session,
so it holds only what changes *how the tools are used* — a rule earns its place
by making an assistant behave differently, not by being true. When adding
something, apply that test first.
